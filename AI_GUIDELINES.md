# AI Interaction Guidelines

## Purpose
Define how the AI should behave when generating artifacts for this project. These guidelines ensure consistency, quality, and predictability across all AI-generated outputs.

---

## 1. General Behavior

### 1.1 Context Loading
Before generating any artifact, the AI MUST:
1. Read the `PHASE_GUIDE.md` of the current phase
2. Read all input documents listed in the phase guide
3. Read the `GOVERNANCE.md` for applicable rules
4. Check `TRACEABILITY.md` for existing links
5. Review `DECISION_LOG.md` for relevant past decisions

### 1.2 Output Format
- All documentation in Markdown format
- All code in the language specified in `40-design/USER_INPUT.md`
- Use consistent heading levels (H1 for title, H2 for sections, H3 for subsections)
- Include a header block in every generated file:

```markdown
<!--
Generated by: AI
Phase: [XX]
Date: [YYYY-MM-DD]
Input documents: [list]
Traces to: [upstream artifact IDs]
-->
```

### 1.3 Communication Style
- Be precise and unambiguous
- Use "shall" for mandatory requirements
- Use "should" for recommended approaches
- Use "may" for optional features
- Never use vague terms without quantification

## 2. When to Ask the Human

The AI MUST ask the human when:

| Situation | Example |
|-----------|---------|
| Ambiguous requirement | "REQ-003 says 'fast response' — what is the target in milliseconds?" |
| Conflicting inputs | "PRI-002 says minimize cost, but REQ-007 requires premium cloud services" |
| Missing information | "No database preference specified — shall I choose based on requirements?" |
| High-impact decision | "This architecture choice will make future scaling expensive. Confirm?" |
| Multiple valid options | "Three valid approaches exist: [A], [B], [C]. Which do you prefer?" |

The AI should NOT ask when:
- The decision is purely technical with no business impact
- The answer can be derived from existing approved documents
- The choice is between equally valid implementation details

## 3. Prompt Templates for Each Phase

### Phase 00 → 10: Generate Requirements
```
CONTEXT:
- Read: 00-principles/PRINCIPLES.md (approved)
- Read: 00-principles/USER_INPUT.md (original input)

TASK:
Generate a Software Requirements Specification (SRS) that:
1. Decomposes each user story into atomic requirements
2. Assigns IDs: REQ-FUNC-XXX, REQ-NFR-XXX, REQ-INT-XXX, REQ-DATA-XXX
3. Each requirement has: Description, Rationale, Source, Priority, Acceptance Criterion
4. Traces each requirement to a principle (PRI-XXX)
5. Identifies any gaps or ambiguities to escalate

OUTPUT: 10-requirement/REQUIREMENTS.md
```

### Phase 10 → 20: Generate Functional Specification
```
CONTEXT:
- Read: 10-requirement/REQUIREMENTS.md (approved)
- Read: 00-principles/PRINCIPLES.md

TASK:
Generate a Functional Specification that:
1. Groups requirements into functional areas
2. Creates detailed use cases (primary, alternative, exception flows)
3. Defines the logical data model
4. Specifies all interfaces
5. Assigns IDs: SPEC-XXX, UC-XXX
6. Traces each spec to requirements

OUTPUT: 20-functional_specification/FUNCTIONAL_SPEC.md, USE_CASES.md, DATA_MODEL.md
```

### Phase 20 → 40: Generate Design
```
CONTEXT:
- Read: 20-functional_specification/FUNCTIONAL_SPEC.md (approved)
- Read: 20-functional_specification/DATA_MODEL.md
- Read: 40-design/USER_INPUT.md (technology preferences)

TASK:
Generate system architecture and detailed design that:
1. Selects appropriate architecture style
2. Decomposes into components with clear responsibilities
3. Designs APIs (OpenAPI format)
4. Transforms logical data model to physical schema
5. Documents all decisions as ADRs
6. Assigns IDs: DES-XXX, ADR-XXX

OUTPUT: 40-design/ARCHITECTURE.md, DETAILED_DESIGN.md, API_DESIGN.md, DATA_DESIGN.md
```

### Phase 40 → 50: Generate Implementation
```
CONTEXT:
- Read: 40-design/ARCHITECTURE.md (approved)
- Read: 40-design/DETAILED_DESIGN.md
- Read: 40-design/API_DESIGN.md
- Read: 40-design/DATA_DESIGN.md

TASK:
Generate production-quality source code that:
1. Implements each component from the design
2. Follows SOLID principles
3. Includes full documentation (docstrings)
4. Implements APIs exactly as specified
5. Includes build configuration
6. No hardcoded values, secrets, or dead code

OUTPUT: 50-implementation/src/
```

### Phase 50 → 60: Generate Tests
```
CONTEXT:
- Read: 60-test_implementation/USER_INPUT.md (critical scenarios)
- Read: 10-requirement/REQUIREMENTS.md (acceptance criteria)
- Read: 20-functional_specification/USE_CASES.md
- Read: 50-implementation/src/ (code to test)

TASK:
Generate comprehensive test suites that:
1. Cover all critical scenarios from user input
2. Test every acceptance criterion
3. Include unit, integration, and E2E tests
4. Follow AAA/Given-When-Then patterns
5. Generate test data (valid + invalid)
6. Achieve ≥80% coverage target

OUTPUT: 60-test_implementation/tests/, TEST_PLAN.md, TEST_CASES.md
```

### Phase 60 → 80: Generate Deployment
```
CONTEXT:
- Read: 80-deployment/USER_INPUT.md (environment details)
- Read: 40-design/DEPLOYMENT_DESIGN.md
- Read: 50-implementation/BUILD.md

TASK:
Generate deployment artifacts that:
1. Infrastructure-as-Code for target platform
2. Container configuration (if applicable)
3. CI/CD pipeline configuration
4. Environment-specific configurations
5. Monitoring and alerting setup
6. Operational runbook

OUTPUT: 80-deployment/infrastructure/, docker/, ci-cd/, config/, monitoring/
```

### Phase 80 → 90: Execute Tests & Report
```
CONTEXT:
- Read: 60-test_implementation/TEST_PLAN.md
- System deployed in staging environment
- All tests available

TASK:
Execute all tests and generate:
1. Test execution report with pass/fail counts
2. Coverage report
3. Defect log with severity classification
4. Release recommendation (GO/NO-GO/CONDITIONAL)
5. Evidence collection

OUTPUT: 90-test_execution/TEST_REPORT.md, COVERAGE_REPORT.md, RELEASE_RECOMMENDATION.md
```

## 4. Quality Checks (Self-Validation)

Before presenting any generated artifact, the AI MUST verify:

| Check | Description |
|-------|-------------|
| Completeness | All required sections are present |
| Traceability | All items trace to upstream artifacts |
| Consistency | No contradictions within the document |
| Naming | IDs follow the naming convention |
| Format | Follows the artifact template |
| No assumptions | All assumptions are explicitly stated |
| Testability | All requirements/specs are testable |

## 5. Error Handling

If the AI encounters an issue during generation:

1. **STOP** generation
2. **Document** the issue clearly
3. **Propose** solutions (2-3 options)
4. **Wait** for human decision
5. **Record** the decision in DECISION_LOG.md
6. **Resume** generation with the decision applied
